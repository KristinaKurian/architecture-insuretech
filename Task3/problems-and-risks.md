# Анализ проблем и рисков текущей архитектуры

## 1. Сильная синхронная связанность

`core-app` и `ins-comp-settlement` зависят от синхронного REST API `ins-product-aggregator`.

`ins-product-aggregator`, в свою очередь, во время запроса обращается к API нескольких страховых компаний. Поэтому задержка или недоступность одной внешней системы влияет на весь synchronous call chain.

## 2. Рост fan-out при подключении новых страховых компаний

Сейчас `ins-product-aggregator` взаимодействует с пятью страховыми компаниями. После подключения ещё пяти число внешних интеграций удвоится.

Риски:

- увеличение среднего и p95/p99 latency;
- рост вероятности partial failure;
- увеличение количества одновременно открытых соединений;
- рост нагрузки на `ins-product-aggregator`;
- повышение вероятности timeout внутренних клиентов.

## 3. Дублирование одинаковых запросов

`core-app` и `ins-comp-settlement` независимо получают практически одинаковые данные о продуктах и тарифах.

Это создаёт лишнюю нагрузку как на `ins-product-aggregator`, так и на внешние API страховых компаний.

## 4. Polling вместо распространения изменений

`core-app` выполняет синхронизацию каждые 15 минут, а `ins-comp-settlement` — один раз в сутки.

Последствия:

- данные между сервисами могут отличаться;
- обновление передаётся с задержкой;
- даже при отсутствии изменений выполняются повторные запросы;
- частота обновления жёстко связана с расписанием клиента.

## 5. Ошибки внешних API распространяются внутрь системы

Timeout, HTTP 5xx или деградация одной страховой компании могут приводить к ошибкам ответа `ins-product-aggregator`, которые далее влияют на `core-app` и `ins-comp-settlement`.

Это увеличивает blast radius внешнего сбоя.

## 6. Ночной batch-запрос settlement → core-app

`ins-comp-settlement` раз в сутки запрашивает у `core-app` все оформленные страховки.

Риски:

- большой единовременный объём данных;
- нагрузка на `core-app` и его БД;
- необходимость повторять весь запрос при частичном сбое;
- жёсткая временная связанность сервисов;
- settlement зависит от доступности `core-app` в момент формирования реестра.

## 7. Локальные реплики данных синхронизируются ненадёжно

Локальные копии продуктов полезны для чтения, но сейчас механизм их обновления основан на REST polling.

При сбоях возможны:

- пропуски обновлений;
- длительное рассогласование данных;
- отсутствие понятного механизма replay;
- сложность восстановления состояния после простоя потребителя.

## 8. Риск потери событий при наивной публикации

Если после записи бизнес-данных сервис сразу отправляет событие в брокер, возможна ситуация:

```text
COMMIT в PostgreSQL выполнен
Kafka publish завершился ошибкой
```

Поэтому события, связанные с изменением локального состояния, должны публиковаться через **Transactional Outbox**.

## Выбранное решение

Использовать Kafka как Event Streaming platform:

- `insurance.products.updated` — изменения продуктов и тарифов;
- `insurance.policy.issued` — оформленная страховка.

`core-app` и `ins-comp-settlement` становятся независимыми consumers и поддерживают собственные read models.

Результат:

- меньше синхронных зависимостей;
- внешние сбои не блокируют внутренний request path;
- события можно повторно прочитать;
- новые consumers можно подключать без изменения producer;
- нагрузка не растёт линейно от количества внутренних получателей данных.
