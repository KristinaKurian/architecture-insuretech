# Анализ проблем и рисков текущей архитектуры

## 1. Синхронная связанность сервисов

`core-app` и `ins-comp-settlement` зависят от REST API `ins-product-aggregator`.

При вызове `ins-product-aggregator` обращается к API всех страховых компаний. Поэтому задержка или недоступность внешнего API влияет на внутреннюю цепочку вызовов.

## 2. Рост fan-out при подключении новых страховых компаний

Сейчас `ins-product-aggregator` работает с пятью страховыми компаниями. После подключения ещё пяти количество внешних интеграций удвоится.

Основные риски:

- рост среднего и p95/p99 latency;
- увеличение вероятности partial failure;
- рост количества внешних соединений;
- увеличение нагрузки на `ins-product-aggregator`;
- повышение вероятности timeout внутренних клиентов.

## 3. Дублирование запросов

`core-app` и `ins-comp-settlement` независимо получают данные о продуктах и тарифах.

Это создаёт повторную нагрузку на `ins-product-aggregator` и внешние API, хотя потребителям нужны одни и те же данные.

## 4. Polling вместо передачи изменений

`core-app` обновляет локальную копию каждые 15 минут, а `ins-comp-settlement` — один раз в сутки.

Последствия:

- данные между сервисами могут быть временно рассогласованы;
- изменения распространяются с задержкой;
- запросы выполняются даже при отсутствии изменений;
- частота синхронизации определяется расписанием потребителя.

## 5. Распространение ошибок внешних API

Timeout, HTTP 5xx и деградация одной страховой компании могут влиять на ответ `ins-product-aggregator`, а затем и на вызывающие внутренние сервисы.

Это увеличивает blast radius внешнего сбоя.

## 6. Ночной batch-запрос settlement → core-app

`ins-comp-settlement` раз в сутки запрашивает у `core-app` все оформленные за день страховки.

Риски:

- большой единовременный объём данных;
- дополнительная нагрузка на `core-app` и его БД;
- необходимость повторять запрос при сбое;
- зависимость settlement от доступности `core-app` в момент формирования реестра.

## 7. Ненадёжная синхронизация локальных копий

Локальные read models полезны для быстрого чтения, но REST polling не даёт удобного механизма replay и усложняет восстановление состояния после длительного простоя потребителя.

## 8. Риск потери события

Если сервис сначала сохраняет бизнес-данные, а затем отдельно публикует событие в Kafka, возможна ситуация:

```text
COMMIT в PostgreSQL выполнен
Kafka publish завершился ошибкой
```

Поэтому для критичных событий требуется **Transactional Outbox**.

## Вывод

Проблема текущей схемы — не в наличии локальных копий данных, а в механизме их синхронизации через периодические REST-запросы.

Целевое решение:

- Kafka для Event Streaming;
- `insurance.products.updated` для продуктов и тарифов;
- `insurance.policy.issued` для оформленных страховок;
- Transactional Outbox;
- идемпотентные consumers;
- retry / DLQ для ошибок обработки.
