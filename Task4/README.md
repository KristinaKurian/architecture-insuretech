# Task4. Проектирование продажи ОСАГО

## Цель

Спроектировать процесс онлайн-оформления ОСАГО для нагрузки до **2 500 одновременных пользователей**.

Основные требования:

- заявка пользователя отправляется во все доступные страховые компании;
- ответы страховых компаний могут приходить в разное время;
- каждое предложение должно отображаться пользователю сразу после получения;
- максимальное время ожидания — **60 секунд**;
- сервисы работают в нескольких экземплярах.

## 1. osago-aggregator

Для взаимодействия со страховыми компаниями выделяется отдельный сервис `osago-aggregator`.

Его ответственность:

- получение задания на расчёт ОСАГО;
- создание заявок во всех доступных страховых компаниях;
- сохранение внешних идентификаторов заявок;
- polling API страховых компаний;
- публикация каждого полученного предложения;
- завершение обработки после получения всех ответов либо достижения установленного deadline.

Функциональность оформления ОСАГО и работа с пользовательской заявкой остаются в `core-app`.

## 2. Хранилище osago-aggregator

`osago-aggregator` требуется собственное хранилище PostgreSQL.

В нём сохраняются:

- `application_id`;
- идентификатор страховой компании;
- внешний `request_id`;
- статус запроса;
- полученное предложение;
- количество попыток;
- `next_poll_at`;
- `deadline`;
- информация о технических ошибках.

Хранилище необходимо, поскольку обработка заявки является асинхронной и должна корректно восстанавливаться после рестарта pod.

## 3. Интеграция core-app ↔ osago-aggregator

Основной механизм интеграции — **асинхронный API через Kafka**.

`core-app` публикует:

```text
osago.application.requested
```

`osago-aggregator` публикует:

```text
osago.offer.received
osago.application.completed
```

Kafka message key — `application_id`, чтобы сохранять порядок событий одной заявки.

Синхронный REST между `core-app` и `osago-aggregator` в основном пользовательском workflow не используется.

## 4. API и интеграция Web ↔ core-app

Для создания заявки используется REST:

```http
POST /api/v1/osago/applications
```

Ответ:

```http
202 Accepted
```

Текущее состояние заявки можно получить:

```http
GET /api/v1/osago/applications/{applicationId}
```

Для доставки новых предложений в реальном времени используется **Server-Sent Events (SSE)**:

```http
GET /api/v1/osago/applications/{applicationId}/offers/stream
```

REST используется для создания заявки и получения текущего состояния, а SSE — для доставки новых предложений сразу после их появления.

SSE выбран вместо WebSocket, потому что realtime-поток в этом сценарии односторонний:

```text
core-app → web application
```

## 5. Работа нескольких replicas

### core-app

SSE-соединение пользователя может быть установлено с одним pod `core-app`, а Kafka-событие может быть обработано другим pod.

Для передачи realtime-уведомлений между replicas используется Redis Pub/Sub:

```text
Kafka → core-app → Redis Pub/Sub → core-app replica → SSE → Web
```

Redis используется как realtime backplane и не является источником истины. Состояние заявки и полученные предложения сохраняются в PostgreSQL `core-app`, поэтому после reconnect клиент может восстановить актуальные данные через REST.

### osago-aggregator

`osago-aggregator` масштабируется горизонтально.

Состояние polling хранится в PostgreSQL. Worker атомарно захватывает задачу через lease либо `SELECT ... FOR UPDATE SKIP LOCKED`, а обработка выполняется идемпотентно.

Kafka использует `application_id` как message key для сохранения порядка событий одной заявки.

## 6. Паттерны отказоустойчивости

При взаимодействии `osago-aggregator → страховая компания` паттерны применяются независимо для каждого страховщика.

| Паттерн | Применение |
|---|---|
| **Timeout** | Ограничение времени каждого HTTP-запроса в рамках общего deadline 60 секунд |
| **Retry** | Exponential Backoff + Jitter для временных ошибок |
| **Circuit Breaker** | Отдельный Circuit Breaker для каждой страховой компании |
| **Rate Limiting** | Отдельный лимит запросов для каждого внешнего API и public API `core-app` |

Retry применяется только к безопасным или идемпотентным операциям.

Сбой одной страховой компании не должен блокировать взаимодействие с остальными страховщиками.

## 7. Deadline 60 секунд

Для каждой заявки фиксируется общий deadline **60 секунд**.

Предложения публикуются независимо друг от друга сразу после получения.

По истечении deadline обработка завершается, даже если часть страховых компаний не ответила. Все уже полученные предложения сохраняются и остаются доступны пользователю.
