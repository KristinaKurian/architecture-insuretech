# Task4. Проектирование продажи ОСАГО

## Цель

Спроектировать оформление ОСАГО при пиковой нагрузке до **2 500 одновременных пользователей**.

Требования:

- заявка направляется во все доступные страховые компании;
- предложение каждой компании отображается пользователю сразу после получения;
- максимальное время ожидания — **60 секунд**.

## 1. osago-aggregator

Добавляется отдельный сервис `osago-aggregator`.

Его ответственность:

- принимать задания на расчёт ОСАГО;
- отправлять заявки во все доступные страховые компании;
- хранить соответствие внутренних и внешних `request_id`;
- выполнять polling API страховых компаний;
- публиковать каждое полученное предложение;
- завершать обработку после получения всех ответов или достижения deadline 60 секунд.

## 2. Хранилище osago-aggregator

Сервису требуется собственное хранилище.

В PostgreSQL сохраняются:

- `application_id`;
- страховщик;
- внешний `request_id`;
- статус запроса;
- полученное предложение;
- число retry;
- `next_poll_at`;
- deadline;
- техническая информация об ошибках.

Хранилище необходимо, потому что workflow асинхронный и должен корректно восстанавливаться после рестарта pod.

## 3. Интеграция core-app и osago-aggregator

Основной механизм интеграции — **Kafka/Event Streaming**.

`core-app` публикует команду:

```text
osago.application.requested
```

`osago-aggregator` публикует события:

```text
osago.offer.received
osago.application.completed
osago.application.failed
```

Kafka message key — `application_id`, чтобы сохранить порядок событий одной заявки.

Синхронный REST между `core-app` и `osago-aggregator` в основном workflow не используется.

Детальные event contracts описаны в `api-contracts.md`.

## 4. Взаимодействие web-приложения и core-app

Для создания заявки используется обычный REST:

```text
POST /api/v1/osago/applications
```

Ответ — `202 Accepted`, потому что обработка продолжается асинхронно.

Для получения уже накопленного состояния используется:

```text
GET /api/v1/osago/applications/{applicationId}
```

Для доставки новых предложений в реальном времени используется **Server-Sent Events (SSE)**.

SSE выбран вместо WebSocket, потому что после создания заявки основной поток данных односторонний: `core-app → browser`.

Детальные REST/SSE contracts находятся в `api-contracts.md`.

## 5. Несколько replicas core-app

SSE-соединение пользователя может быть установлено с одним экземпляром `core-app`, а Kafka-событие получить другой экземпляр.

Для передачи realtime-уведомлений между replicas используется **Redis Pub/Sub**.

Redis выполняет только роль realtime backplane и **не является источником истины**.

Полученные предложения и статус заявки сохраняются в PostgreSQL `core-app`. Поэтому при потере transient Redis-сообщения клиент может восстановить состояние обычным `GET`.

## 6. Несколько replicas osago-aggregator

`osago-aggregator` масштабируется горизонтально.

Для предотвращения одновременного polling одной и той же заявки несколькими pod используются:

- Kafka key = `application_id`;
- хранение polling jobs в PostgreSQL;
- lease или `SELECT ... FOR UPDATE SKIP LOCKED`;
- идемпотентная обработка.

## 7. Паттерны отказоустойчивости

Для взаимодействия `osago-aggregator → страховые компании` паттерны применяются отдельно для каждого страховщика.

| Паттерн | Решение |
|---|---|
| Timeout | Ограничение времени HTTP-вызова; общий deadline всей обработки — 60 секунд |
| Retry | Exponential backoff + jitter для временных ошибок |
| Circuit Breaker | Отдельный circuit breaker для каждого страховщика |
| Rate Limiting | Отдельный лимит запросов для каждого внешнего API |

Дополнительно:

- retry не должен выходить за общий deadline;
- при открытом circuit breaker остальные страховщики продолжают обрабатываться независимо;
- при наличии поддержки внешнего API используется idempotency key.

Для public API `core-app` применяется Rate Limiting.

Для SSE используются heartbeat и reconnect.

Для Kafka предусматриваются:

- retry topic;
- DLQ;
- idempotent consumers;
- correlation по `application_id`.

## 8. Ключевой принцип обработки

Система не ожидает ответы всех страховых компаний в одном синхронном запросе.

После создания заявки пользователь получает `202 Accepted`, а каждое предложение передаётся через SSE сразу после появления.

Через 60 секунд workflow завершается, даже если часть страховых компаний не ответила.
